# GymFlow — Product Specification (Single Source of Truth)

This file is the ONLY source of truth for scope. Every requirement has:
- a phase tag like `[P2]` (the phase in which it must be completed), and
- a unique ID like `MEM-04`.

Rules for the AI agent:
1. A requirement is "done" only when it is implemented end-to-end (DB + RLS + server + UI + validation + tests where listed) and ticked in `PROGRESS.md` with evidence (file paths + test names).
2. Never silently drop, merge or reinterpret a requirement. If something is impossible or deferred, write it in `PROGRESS.md` under "Known gaps" with the reason.
3. Section 0 (Resolved Decisions) overrides any ambiguity elsewhere.

## 0. RESOLVED DECISIONS (read first — these remove ambiguity)

- [P0] **DEC-01** Timezone: store all timestamps as `timestamptz` (UTC). "Today", "this month", expiry and reminders are computed in the gym's timezone (`gyms.timezone`, default `Asia/Kolkata`). Never use the server's local time.
- [P0] **DEC-02** Money: store all amounts as `bigint` in minor units (paise). All calculations use integer math via a shared `money` utility. Never use JS floating point for money. Display formatted with gym currency (default INR, `en-IN` grouping).
- [P0] **DEC-03** Membership dates: `end_date = start_date + plan duration − 1 day` (inclusive). Month-based plans use calendar-month addition (e.g., 31 Jan + 1 month → 28/29 Feb, then −1 day logic applied consistently and unit-tested). Membership is active when `start_date ≤ today ≤ end_date` in gym timezone. `days_remaining = end_date − today` (0 on last day).
- [P0] **DEC-04** Freeze: freezing records a `membership_freezes` row (start, end, reason). On resume, `end_date` is extended by the frozen days. Total frozen days cannot exceed the plan's `freeze_days`. Attendance is blocked while frozen.
- [P0] **DEC-05** Membership status is derived: `upcoming | active | frozen | expired | cancelled`. Member status (`active | inactive | frozen | suspended | expired | archived`) is updated by (a) triggers on membership changes and (b) a nightly job. Manual statuses (`suspended`, `archived`) are never overwritten by automation.
- [P0] **DEC-06** Tax / GST: gym setting `gst_registered` (default false). If true: GSTIN required, rate configurable (no hard-coded rate in code; seed may use 18%), prices configurable as tax-inclusive or tax-exclusive. Intra-state → split into CGST + SGST equally; inter-state → IGST. Default place of supply = gym's state. Rounding to nearest paisa per line, documented and tested. If not registered, no tax lines and no GSTIN on invoices.
- [P0] **DEC-07** Invoice numbering: per gym, per Indian financial year (1 Apr – 31 Mar), configurable prefix, e.g. `GF/2026-27/0001`. Generated by a Postgres function using a locked counter row (concurrency-safe, no gaps, never reused). Invoices are never deleted; refunds create a credit note / refund record.
- [P0] **DEC-08** Member code: per-gym sequential with configurable prefix (e.g. `GF-0001`), generated in DB, unique per gym.
- [P0] **DEC-09** QR code content: an opaque, regenerable `qr_token` (random UUID or HMAC-signed token). Never encode phone, email, name or raw DB id. Staff can regenerate a member's QR (old one stops working).
- [P0] **DEC-10** Attendance duplicates: a member can have only one open check-in at a time (partial unique index). A repeat scan within a configurable window (default 10 min) is ignored with a clear message. A scan while checked-in performs check-out if "scan-to-checkout" is enabled in settings. Open check-ins are auto-closed at gym closing time by the nightly job (flagged `auto_closed`).
- [P0] **DEC-11** Grace access: setting `grace_days` (default 0). Expired members are refused with "Membership Expired" unless within grace days AND grace is enabled; grace check-ins are flagged.
- [P0] **DEC-12** Soft delete: `deleted_at` on members, trainers, staff, plans, products, equipment, expenses, templates, automations. Payments, invoices, attendance and audit logs are never deleted (void/refund/correct only). Unique constraints use partial indexes `WHERE deleted_at IS NULL`.
- [P0] **DEC-13** Phone numbers: stored in E.164. Default country +91; Indian mobiles validated as 10 digits starting 6–9. Other countries allowed when gym country differs.
- [P0] **DEC-14** Date display format is a gym setting (default `DD/MM/YYYY` for India).
- [P0] **DEC-15** Users vs members vs staff: Supabase `auth.users` is identity. `profiles` (1:1 with auth user) holds name/phone/avatar. Staff membership in a gym = `gym_staff` + `user_roles`. `members` is a gym record that MAY link to an auth user (`members.user_id`, nullable) for portal access. A member without email is fully valid (no portal login). Trainers are staff with a `trainers` profile row.
- [P0] **DEC-16** Scheduler: reminders/nightly jobs run via Supabase `pg_cron` calling a DB function or Edge Function (primary). Optionally a Vercel Cron route protected by `CRON_SECRET` (note: Vercel's free plan limits cron frequency — verify current limits). All jobs are idempotent.
- [P0] **DEC-17** Reminder idempotency: `reminder_logs` has a unique key `(automation_id, entity_type, entity_id, occurrence_date, channel)` so a reminder is never sent twice for the same event.
- [P0] **DEC-18** Files: private Supabase Storage buckets, path `{gym_id}/{entity}/{id}/{filename}`, storage RLS by gym, access via short-lived signed URLs. Logos may use a public bucket.
- [P0] **DEC-19** Health & privacy: health notes, measurements and progress photos are visible only to the member, their assigned trainer/nutritionist, and roles with `progress.view`. Member registration includes a consent checkbox for storing health data and photos (India DPDP Act awareness; not legal advice).
- [P0] **DEC-20** Onboarding needs plans & trainers: the `membership_plans`, invitations and `trainers` tables are created in Phase 1 migrations so onboarding steps 7–8 work; full management UIs come in Phase 2.
- [P0] **DEC-21** All app URLs come from `NEXT_PUBLIC_APP_URL`. Nothing references `gymflow.vercel.app` directly, so a custom domain can be added later with only env + DNS changes. (Note: that exact subdomain may already be taken; any free `*.vercel.app` name works.)
- [P0] **DEC-22** Ambiguity rule: if a detail is not specified, choose the simplest secure option, implement it, and record it in `docs/DECISIONS-LOG.md`. Do not stop work to ask about minor details.

## 1. GENERAL ENGINEERING RULES

- [P1] **GEN-01** TypeScript `strict: true` everywhere. No `any` unless justified in a comment.
- [P1] **GEN-02** No hard-coded business data, brand names, prices, tax rates or permissions in code. They come from DB/settings/config.
- [P1] **GEN-03** No secrets in client code. Service-role key is used only in files importing `server-only`.
- [P1] **GEN-04** No sensitive data (tokens, roles, PII) in localStorage/sessionStorage.
- [P1] **GEN-05** No fake APIs or mock data in production code paths. Demo data exists only via seed scripts.
- [P1] **GEN-06** No dead buttons. Every control works, or is visibly disabled with a tooltip explaining why (e.g. "WhatsApp provider not configured").
- [P1] **GEN-07** Reusable components; no duplicated components.
- [P1] **GEN-08** Every data list: server-side pagination, search, filter, sort.
- [P1] **GEN-09** Every mutation: loading state, success toast, friendly error toast. Destructive actions require a confirmation dialog.
- [P1] **GEN-10** Accessibility: labels, keyboard navigation, visible focus, WCAG AA contrast, aria attributes on custom controls.
- [P1] **GEN-11** Mobile-first responsive layout for every page.
- [P1] **GEN-12** Every state handled per page: loading (skeleton), empty, error, permission denied, network failure.

- [P1] **RBAC-04** Default matrix: Owner = all. Manager = members, memberships, attendance, payments, trainers, reports. Receptionist = member registration, attendance, memberships, payments, invoices. Trainer = assigned members, workout, diet, PT, progress. Nutritionist = assigned members, diet, progress. - [P1] **RBAC-06** Branch scope: `user_roles.branch_id` nullable (NULL = all branches).
- [P2] **RBAC-07** Trainer/nutritionist see only members assigned to them (`trainer_members`).
- [P4] **RBAC-08** Member sees only own records (enforced in RLS via `members.user_id = auth.uid()`).
- [P1] **RBAC-09** Tests prove each role can/can't perform representative actions.
- [P7] **RBAC-10** Permission matrix UI in settings: view all, edit custom roles, system roles read-only.

## 6. MULTI-TENANCY
- [P1] **TEN-01** Every tenant table has `gym_id NOT NULL` FK; branch-scoped tables also have `branch_id`.
- [P1] **TEN-02** RLS enabled on EVERY table (no exceptions). Helper functions `is_gym_staff(gym_id)`, `has_permission(gym_id, perm, branch_id)` are `SECURITY DEFINER`, `STABLE`, with fixed `search_path`.
- [P1] **TEN-03** Child rows must match parent gym (composite FKs or validation triggers), e.g. a payment's member must be in the same gym.
- [P1] **TEN-04** A user may belong to multiple gyms. Active gym/branch switcher; selection stored in a cookie (id only) and re-validated server-side on every request.
- [P1] **TEN-05** Tenant isolation tests: Gym A user cannot select/insert/update/delete Gym B rows for every table.
- [P9] **TEN-06** Super-admin area (`/admin`) to view gyms, suspend a gym, view subscription; all actions audited.
